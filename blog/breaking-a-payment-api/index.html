Breaking a Payment API

I tested the API behind a bill-payment service. The bugs that mattered were in the workflow: the order of the steps, what a simple “read” quietly changed, and what happened when two requests arrived at once. Here is how I found six of them by treating the API as a state machine.

01 · The setup

Three parties, one target

A bill-payment aggregator sits in the middle of a chain that moves money. On one end is a merchant: here, a bank whose app lets customers pay bills. In the middle is the aggregator, one API that takes each payment and passes it on. On the far end are the billers, the top-up, electricity, insurance, and mobile-money services that actually fulfil the payment.

I was allowed to test the aggregator only. Not the bank’s app, not the customer, not the billers. So the whole test surface is the link between the merchant and the aggregator.

Every request carried two sets of credentials. One identified the merchant (in the headers), and one picked the biller (in the body). The second set looked like a second password. It wasn’t. Those biller keys were the same for every merchant, and were handed out by a public list endpoint. So the only real gate is the merchant credential. Worth remembering.

Before sending any live traffic, I had a saved copy of the API’s requests and responses to read. An hour with those gave me the map that everything below is built on.

02 · The method

Treat the API as a state machine

At its core the API is a payment that moves through a few states. It is created, then submitted, then either settled or failed. Drawing that little machine makes the rules it must always obey obvious. Two of the six findings are right there in the picture: places where the payment made a move that should be impossible.

The state machine covers the workflow. A payment API also owes a few plainer promises no matter what: it should not let one caller flood it, it should not store dangerous input, and it should bound every amount. That is six promises in all. I went through the list and tried to break each one.

03 · The findings

Six promises, and how each one broke

Finding 1

A single request permanently blocks a pending payment

The promise: a live payment survives a status check or a failed attempt.

What I did. Created a pending payment. Then, on that same transaction, I either just checked its status, or sent a payment that got rejected (wrong biller keys, or a missing field).

What happened. Any of those requests consumed the transaction. Its ID could no longer be used to pay. The correct payment sent afterwards was rejected, and the transaction was stuck in a dead, unpayable state.

create a payment                     → PENDING
check its status  OR  pay w/ wrong keys  → the transaction is consumed
pay with the correct keys            → rejected, the payment is dead

I ruled out a timeout. Paying immediately worked. Adding the same delay by checking a different transaction worked. Only touching this transaction killed it.

Why it matters. This is a denial of service against payments. Because any request that reaches a pending transaction consumes it, an attacker who knows or guesses a transaction ID can permanently block a customer’s payment with a single cheap request that does not even need to succeed. A benign status check, or one wrong key, is enough.

Finding 2

The payment step could be skipped entirely

The promise: nothing is marked paid until the pay step is actually called.

What I did. On four billers, I checked the status right after the lookup step, before calling pay at all.

What happened. The status already showed successful. Calling pay afterwards changed nothing.

Why it matters. The pay step is meant to be the authorization gate for a payment. On these billers it enforces nothing. A transaction reports as fully paid using only the lookup step, which needs just the standard credentials, so the gate that should protect the payment is effectively open.

Finding 3

No limit on how fast a caller can hit the API

The promise: one caller cannot send unlimited requests.

What I did. Sent a burst of requests to the same endpoint from a single credential.

What happened. Every request was accepted. No throttling, no lockout, and no “too many requests” response at any point.

Why it matters. With no limit, one caller can drive the API at full speed. That removes the natural cost barrier behind every other attack: brute forcing IDs, enumerating the catalog, and hammering the payment operations. It also lets a single caller create pending transactions without any bound, filling the system with junk records.

Finding 4

Two requests at once slipped past the rules

The promise: one transaction is paid once, even when requests arrive together.

What I did. Sent five payments for the same transaction at the exact same moment. Then sent several create requests that all used the same ID at once.

What happened. Instead of one success and the rest cleanly rejected, several payments succeeded (all sharing one reference), and others returned raw internal errors. The create race produced several records for a single ID. Sent one at a time, everything behaved.

Why it matters. The uniqueness the transaction ID is supposed to guarantee only holds when requests arrive one at a time. A race defeats the duplicate check and can leave the transaction in an inconsistent state.

Finding 5

Script markup was stored straight into payment records

The promise: attacker-controlled text is neutralised before it is stored.

What I did. Put HTML and script markup into free-text fields, such as a name, then completed the payment.

What happened. The markup was accepted, stored, and returned exactly as sent, with no escaping. It ended up bound into a completed payment record.

Why it matters. Any application that later shows this record in a web page (a receipt, a saved-payee list, a transaction history, an internal dashboard) and does not escape it will run the attacker’s script. The value comes back as JSON, so it does not execute at the API itself. The vulnerability is that the API stores active, attacker-controlled markup inside a financial record with no neutralisation, a stored cross-site-scripting sink waiting for a place to render.

Finding 6

Some billers accepted any amount, up to a billion

The promise: every amount is bounded by one shared check.

What I did. Sent very small and very large amounts to different billers.

What happened. Top-up billers enforced a sensible range. But the insurance, club, and ISP billers accepted anything, from a single unit up to nine digits, and settled it.

top-up biller     amount = 1,000,000,000   → rejected  range enforced
insurance biller  amount = 1,000,000,000   → SETTLED   accepted and paid
insurance biller  amount = 1               → SETTLED   no floor either

Why it matters. With no ceiling, one request settles an enormous charge, and nothing stops a mistake or an abuse. The fact that some billers enforce a range while others enforce nothing shows the check is duplicated per biller instead of applied once, so an attacker only has to find the biller where it was left off, and the next biller added inherits the same gap.

04 · The pattern

None of these were exotic

Each finding is one promise the API makes, and one request that breaks it. That is the whole method. Map the payment as a state machine, list the promises it must keep, then try to make each one false.

These are not header or certificate bugs. They live in the order of the steps, in reads that quietly change state, and in what happens when requests race. That is where the security risk in a payment API concentrates, and where it takes deliberate, manual testing to find.

The takeaway

Before you poke an API, map its state machine and write down the promises it must keep. Then go break them, one at a time. That list is your test plan.

On anonymisation. Every identifier here (the parties, the endpoint names, the biller categories, the status values, the amounts) is generalised or invented. This describes a class of system and a way of testing it, not any specific product, provider, or engagement. Nothing here reproduces client data.
